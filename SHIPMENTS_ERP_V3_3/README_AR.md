# SHIPMENTS ERP V3 — برج المراقبة الذكي

## ما الذي أُضيف؟
- شاشة Control Tower موحدة لمؤشرات التسليم وCOD والفجوة بين التحصيل والتوريد.
- مركز استثناءات مع بحث وفلاتر حسب الخطورة والنوع.
- ملف مراجعة لكل شحنة يعرض العميل والمستلم والفرع والمندوب وقيم COD.
- مقارنة أداء الفروع وتوصيات مبنية على قواعد توضيحية.
- تصدير الاستثناءات إلى CSV.
- مسودة PostgreSQL تشمل الفروع والعملاء والمندوبين والشحنات والتحصيلات وتسويات المندوبين وسجل التدقيق.
- FastAPI scaffold لنقاط فحص تخصيص الدفعات ومطابقة COD.

## تشغيل العرض
افتح `index.html` مباشرة في متصفح الهاتف أو الكمبيوتر. لا يحتاج إلى Terminal أو تثبيت.

## مهم جدًا
جميع بيانات لوحة V3 بيانات افتراضية للعرض فقط. لا يوجد اتصال بقاعدة بيانات أو نظام تتبع أو بوابة دفع أو خزينة فعلية. لا تعتمد أي تسوية مالية من هذه الشاشة. ملف `schema.sql` مسودة غير مطبقة.

## تشغيل اختبارات الواجهة

`node tests/control_tower.test.cjs`

## المرحلة الإنتاجية التالية
1. اعتماد دورة COD ومصفوفة الصلاحيات والفروع.
2. إعداد PostgreSQL سحابي وربط الأسرار في بيئة الخادم فقط.
3. تنفيذ المصادقة، RBAC، سجل التدقيق، القيود المحاسبية، قفل الصفوف والمعاملات الذرية.
4. بناء API حقيقية وربط الواجهة بها.
5. استيراد بيانات الشركة بعد تنظيفها ومراجعتها، ثم اختبارات قبول وموافقة منفصلة قبل أي ترحيل إنتاجي.

## V3.2 — دفتر عهدة المندوب

أضيفت شاشة «دفتر حركة عهدة المندوب» لتسجيل الرصيد الافتتاحي، والتحصيل، والتوريد، والتسويات الدائنة. كل حركة تحمل رقمًا مرجعيًا وتاريخًا وسببًا ورصيدًا متحركًا. لا توفر الواجهة تعديلًا أو حذفًا للحركة؛ التصحيح يتم بإضافة قيد عكسي مرتبط بالأصل. يمكن تصدير الدفتر CSV.

### واجهة العرض
- تعمل الواجهة الثابتة دون خادم، وتحفظ حركات دفتر العرض في `localStorage` على الجهاز الحالي فقط.
- هذه ليست حماية محاسبية حقيقية: يمكن العبث بتخزين المتصفح من خارج الواجهة، ولا توجد مصادقة أو أدوار مستخدمين.
- استخدم بيانات اصطناعية فقط. لا تعتمد أو ترحّل أموالًا فعلية من نسخة العرض.

### API محلي تجريبي
- `POST /v1/couriers/ledger` لإضافة حركة عهدة.
- `GET /v1/couriers/{courier_code}/ledger` لقراءة دفتر المندوب ورصيده.
- `POST /v1/couriers/ledger/{reference_no}/reverse` لإضافة قيد عكسي، مع منع عكس الحركة نفسها مرتين.
- يستخدم الـAPI ملف SQLite محليًا، ويمكن تحديد مساره عبر متغير البيئة `SHIPMENTS_LEDGER_DB`. لا يتصل هذا تلقائيًا بواجهة HTML ولا بقاعدة بيانات سحابية.
- تمنع قاعدة SQLite تعديل أو حذف القيود عبر Triggers. أضيف أيضًا مخطط PostgreSQL المقترح في `backend/schema.sql` مع Trigger للحماية.

### قبل الإنتاج
يلزم ربط واجهة المستخدم بالـAPI، واستبدال SQLite بقاعدة PostgreSQL مركزية، وإضافة تسجيل دخول وصلاحيات للفرع والخزينة والمراجع، وتسجيل هوية منشئ الحركة ومعتمدها، وتنفيذ قفل صفوف ومعاملات ذرية، ومراجعة مستقلة لكل قيد، واختبارات ترحيل واستعادة ونسخ احتياطي. لا يوجد اعتماد ضريبي إلكتروني في هذا الإصدار؛ مستند التسوية السابق مستند داخلي فقط.


## V3.3 — تسجيل الدخول والصلاحيات وسجل المراجعة

### ما أضيف إلى API
- تسجيل دخول `POST /v1/auth/login` وإصدار Bearer token موقّع بمدة صلاحية محددة.
- `GET /v1/auth/me` لعرض المستخدم ودوره وصلاحياته.
- إنشاء المستخدمين عبر `POST /v1/admin/users` لمستخدم super_admin فقط.
- أدوار: super_admin، company_manager، branch_manager، treasury، auditor، courier.
- صلاحيات منفصلة لقراءة دفتر العهدة، وإضافة الحركات، وعكس القيود، وإدارة المستخدمين، وقراءة سجل المراجعة.
- تقييد المستخدم المرتبط بفرع على بيانات فرعه، وحساب المندوب على دفتر المندوب المرتبط به.
- `GET /v1/admin/audit` لسجل المراجعة؛ يسجل دخول المستخدمين وإنشاء الحركات وعكسها.
- منع تعديل أو حذف قيود العهدة وسجل المراجعة داخل SQLite التجريبي.
- إعداد مخطط PostgreSQL للمستخدمين وسجل المراجعة وقيود العهدة مع Triggers للحماية.

### إعداد أول مدير
اضبط متغيرات البيئة قبل تشغيل الخادم:
- `SHIPMENTS_BOOTSTRAP_ADMIN_USER`
- `SHIPMENTS_BOOTSTRAP_ADMIN_PASSWORD` (كلمة مرور قوية)
- `SHIPMENTS_AUTH_SECRET` (سر عشوائي طويل وفريد؛ لا تضعه داخل Git أو الواجهة)
- `SHIPMENTS_TOKEN_TTL` (اختياري، الافتراضي 3600 ثانية)
- `SHIPMENTS_LEDGER_DB` (مسار ملف SQLite التجريبي)

عند أول تشغيل، ينشئ API المدير الأول إذا كانت متغيرات المستخدم وكلمة المرور موجودة ولم يكن المستخدم موجودًا. لا توجد بيانات دخول افتراضية مضمّنة.

### تجربة API
1. شغّل الخادم: `uvicorn backend.main:app --host 127.0.0.1 --port 8000`
2. سجّل الدخول إلى `/v1/auth/login` للحصول على `access_token`.
3. أرسل `Authorization: Bearer <token>` مع طلبات دفتر العهدة.
4. راجع `docs/API_V3_3_AR.md` لأمثلة الطلبات.

### حدود النسخة
- التخزين الفعلي الحالي في API هو SQLite محلي تجريبي. مخطط PostgreSQL موجود لكنه لم يطبق على قاعدة سحابية، ولا يوجد `DATABASE_URL` متصل.
- واجهة HTML لا تزال تستخدم localStorage ولا تتصل تلقائيًا بـAPI. ربط الواجهة يحتاج عنوان HTTPS للخادم وآلية إدارة جلسة آمنة.
- المصادقة الحالية أساس تجريبي: لا يوجد بعد MFA أو تدوير Refresh Tokens أو تحديد معدل محاولات الدخول أو إدارة جلسات/إبطال فوري للرموز. يجب وضع API خلف HTTPS وReverse Proxy مع rate limiting قبل الإنتاج.
- صلاحيات الفرع محددة في API التجريبي؛ اعتماد دورة العمل والفصل بين منشئ الحركة ومعتمدها يحتاج سير موافقات كاملًا قبل الاستخدام المالي الحقيقي.
- لا تضع كلمات المرور أو مفاتيح API أو أسرار قاعدة البيانات داخل ملفات HTML أو GitHub.

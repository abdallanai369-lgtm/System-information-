# SHIPMENTS ERP — مسودة نموذج البيانات للـ Backend

> مستند تصميم مبدئي للانتقال من `localStorage` إلى PostgreSQL. لم يُنفّذ على أي قاعدة بيانات، ويحتاج مراجعة قواعد التشغيل والضرائب قبل اعتماده.

## الكيانات الأساسية والعلاقات

- `companies`: كل كيان قانوني مستقل.
- `branches`: تتبع شركة واحدة، ويجب أن تحمل كل حركة تشغيلية/مالية `company_id` و`branch_id` عند انطباقهما.
- `customers`: عميل شركة أو فرد. `account_code` فريد داخل الشركة ولا يتغير عند تعديل الاسم أو الهاتف ولا يعاد استخدامه.
- `employees`: الموظفون والمندوبون، مع فرع أساسي وحالة عمل. الصلاحيات لا تُستنتج من المسمى الوظيفي.
- `shipments`: رقم تتبع فريد، عميل، فرع منشأ/تسليم، مندوب، مستلم، رسوم الشحن، قيمة COD، وحالة تشغيلية.
- `invoices`: رقم فاتورة متسلسل داخل الشركة، عميل، فرع، تاريخ إصدار واستحقاق، إجمالي وضريبة وعملة وحالة اعتماد.
- `invoice_shipments`: ربط الشحنات بالفواتير، مع قيد يمنع فوترة الشحنة مرتين إذا كانت سياسة الشركة فاتورة واحدة لكل شحنة.
- `receipts`: سند قبض مستقل للعميل، بتاريخ ومبلغ وطريقة دفع ومرجع بنكي/نقدي وحالة اعتماد.
- `receipt_allocations`: توزيع سند واحد على فاتورة أو أكثر. كل تخصيص مرتبط بنفس العميل الموجود في السند والفاتورة.
- `customer_statements`: رقم كشف فريد، فترة، أرصدة وإجماليات، ونسخة JSON ثابتة تتضمن بيانات العميل والحركات والأرصدة المتحركة عند الإصدار.
- `cod_collections`: التحصيل من المستلم المرتبط بالشحنة، مع المندوب والتاريخ وطريقة التحصيل وإثباته.
- `cod_settlements` و`cod_settlement_items`: تسوية مبالغ COD المستحقة للعميل التجاري، مع تتبع كل شحنة ومبلغها وخصوماتها.
- `accounts`: شجرة الحسابات لكل شركة.
- `journal_entries` و`journal_lines`: القيود اليومية ورؤوسها وبنودها، مع منع الترحيل إذا لم يتساوَ مجموع المدين والدائن.
- `roles`, `permissions`, `role_permissions`, `user_roles`, `user_branch_access`: الصلاحيات والأدوار ونطاق الوصول للشركات والفروع.
- `audit_logs`: سجل غير قابل للمحو لتغييرات البيانات والاعتمادات والترحيل والعكس.

## قيود سلامة لا بد من فرضها في قاعدة البيانات والخدمة

1. `UNIQUE(company_id, account_code)` للعملاء، و`UNIQUE(company_id, invoice_number)` للفواتير، و`UNIQUE(company_id, receipt_number)` للسندات، و`UNIQUE(company_id, statement_number)` للكشوف.
2. منع تغيير `account_code` بعد إنشاء العميل، ومنع الحذف الفعلي للعميل الذي له حركات؛ يستخدم التعطيل بدل الحذف.
3. المبالغ `NUMERIC(14,2)` وليست `FLOAT`، مع `CHECK(amount >= 0)` حيث ينطبق.
4. تخصيص الدفعة لا يتجاوز مبلغ السند، ولا يتجاوز الرصيد المتبقي للفاتورة، ولا يربط عميلًا بفاتورة عميل آخر.
5. تنفيذ التخصيص داخل معاملة واحدة مع `SELECT ... FOR UPDATE` على السند والفواتير ذات الصلة؛ ثم إعادة فحص المجاميع قبل الحفظ لمنع التخصيص المتزامن الزائد.
6. قيد اليومية لا يُرحّل إلا إذا كان مجموع المدين مساويًا لمجموع الدائن، ولا تعدّل القيود المرحلة؛ التصحيح بقيد عكسي موثق.
7. استخدام مفاتيح idempotency عند استقبال عمليات دفع أو شحن من واجهات خارجية لمنع التكرار.
8. كشف الحساب لقطة محفوظة غير قابلة للتعديل؛ التصحيح يكون بكشف جديد مرتبط بالقديم وسبب واضح.
9. كل إجراء حساس يمر بمسار صلاحية وموافقة، مع فصل منشئ العملية عن معتمدها ومرحلها عند الحاجة.
10. كل طلب مالي يسجل المستخدم والوقت والشركة والفرع ومصدر الحركة والمرجع الخارجي.

## واجهات API المقترحة للمرحلة الأولى

- `POST /customers` — إنشاء عميل وإصدار `Customer Account ID` من sequence داخل قاعدة البيانات.
- `GET /customers/{account_code}/financial-summary` — الفواتير والمقبوضات والتخصيصات والمتبقي والرصيد الدائن وصافي الرصيد.
- `POST /invoices` و`GET /invoices/{invoice_number}`.
- `POST /receipts` — إنشاء سند قبض في حالة مسودة/بانتظار الاعتماد.
- `POST /receipts/{id}/allocations` — تخصيص متعدد الفواتير داخل معاملة ذرية.
- `POST /customers/{account_code}/statements` — إنشاء لقطة كشف حساب لفترة.
- `GET /statements/{statement_number}` — استرجاع النسخة المرجعية كما أُصدرت.

## قرارات يجب حسمها قبل ترحيل قاعدة البيانات

- هل الفوترة لكل شحنة أم مجمعة دوريًا أم الطريقتان؟
- هل العملاء شركات وأفراد معًا؟ (النموذج يدعم النوعين مبدئيًا.)
- هل يوجد فرع واحد أم عدة فروع، وهل لكل فرع خزينة مستقلة؟
- قواعد COD: توقيت استحقاق التسوية، الخصومات والمرتجعات، عمولة التحصيل، وفترة التسوية.
- هل يسمح بتقسيم الشحنة على أكثر من فاتورة؟
- الضرائب المطلوبة وأنواع الفواتير الرسمية والتكامل الضريبي المصري.

## ترتيب تنفيذ Backend المقترح

1. PostgreSQL migrations وقيود الشركات والفروع والعملاء والشحنات والفواتير والسندات والتخصيصات.
2. خدمة الحسابات واختبارات التزامن والتخصيص ولقطات كشوف الحسابات.
3. دفتر الأستاذ والقيود المزدوجة والموافقات وسجل التدقيق.
4. دورة COD وتسويات العملاء وعهد المندوبين.
5. RBAC ونطاقات الفروع والنسخ الاحتياطي والمراقبة.
6. نقل الواجهة من التخزين المحلي إلى API مع خطة ترحيل بيانات ومراجعة أرصدة قبل أي تشغيل فعلي.

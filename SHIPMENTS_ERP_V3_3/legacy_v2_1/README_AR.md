# SHIPMENTS ERP V2.1 — محرك الحسابات والتحصيل

هذه نسخة تطويرية من النموذج التجريبي السابق، وليست نسخة تشغيل إنتاجي.

## ما تغير في V2.1

1. فصل الأرقام المالية بدل جمعها في رقم واحد:
   - **إجمالي المقبوضات:** كل ما استلمه النظام من العميل.
   - **الموزع على الفواتير:** المبالغ التي خُصصت لفواتير بعينها.
   - **المتبقي على الفواتير:** قيمة الفواتير ناقص التوزيعات الصحيحة عليها.
   - **الرصيد الدائن غير الموزع:** المقبوضات التي لم تُخصص لفاتورة.
   - **صافي رصيد العميل:** إجمالي الفواتير ناقص إجمالي المقبوضات.
2. تسجيل دفعة واحدة وتوزيعها على أكثر من فاتورة للعميل نفسه.
3. منع التوزيع على فاتورة عميل آخر، أو تكرار الفاتورة داخل التوزيع، أو تجاوز المتبقي على الفاتورة، أو تجاوز إجمالي التوزيعات قيمة الدفعة.
4. استخدام حسابات بالسنت/القرش داخليًا لتقليل أخطاء الكسور العشرية.
5. تحسين كشف الحساب: رصيد افتتاحي، حركات الفترة، رصيد متحرك بعد كل حركة، إجماليات مدين ودائن، ورقم كشف متسلسل.
6. حفظ اسم العميل وهاتفه ورصيد وحركات الكشف داخل نسخة الكشف وقت الإصدار؛ الحركات أو تغييرات بيانات العميل اللاحقة لا تعيد حساب النسخة القديمة.
7. تحسين توليد أرقام العملاء والفواتير والسندات والكشوف باستخدام أكبر رقم تسلسلي محفوظ، بدل الاعتماد على عدد السجلات فقط.
8. الإبقاء على مفتاح التخزين المحلي القديم `shipments_erp_demo_v1` حتى يستطيع النموذج قراءة بيانات المتصفح السابقة، مع تطبيع الدفعات القديمة التي لا تحتوي على `allocations`.

## التشغيل

- فك ضغط الحزمة.
- افتح `index.html` في متصفح حديث، أو استضف المجلد على خادم ويب ثابت.
- البيانات محفوظة في `localStorage` على نفس المتصفح والجهاز؛ لا توجد مزامنة بين الأجهزة.
- احتفظ بنسخة احتياطية من بيانات المتصفح قبل تجربة بيانات حقيقية.

## الاختبارات

يتطلب تشغيل الاختبارات Node.js 18 أو أحدث، ولا يحتاج إلى حزم خارجية:

```bash
node tests/financial-engine.test.cjs
node tests/smoke-ui.cjs
```

## حدود النسخة الحالية

- لا توجد قاعدة PostgreSQL أو Supabase متصلة.
- لا يوجد Backend أو تسجيل دخول أو RBAC أو فصل شركات وفروع فعلي.
- لا يوجد دفتر أستاذ عام أو قيود يومية مزدوجة أو اعتماد/ترحيل محاسبي.
- COD مسجل كقيمة على الشحنة فقط؛ لا توجد دورة تحصيل وتسوية COD أو مطابقة عهد المندوبين.
- لا توجد إدارة فعلية للفروع والمندوبين والرواتب والمخازن وباقي وحدات ERP.
- الفاتورة الرقمية الحالية للعرض والطباعة داخل النموذج؛ الرابط العام الآمن وQR القابل للتحقق يحتاجان Backend واستضافة.
- لا تعتمد هذه النسخة في التحصيل الحقيقي أو الإقرار الضريبي أو القيود الرسمية.

## قواعد محاسبية مطبقة في النموذج

الدفعة النقدية تُسجل كاملة في حساب العميل كدائن، حتى لو لم توزع بعد. أما حالة كل فاتورة والمتبقي عليها فيعتمدان على المبالغ المخصصة لها فقط. لذلك قد يكون هناك متبقٍ على الفواتير ورصيد دائن غير موزع في الوقت نفسه، ويُعرضان منفصلين. صافي رصيد العميل يساوي الفواتير ناقص المقبوضات.

## الخطوة التالية

تحويل هذا المحرك إلى خدمة API وقاعدة PostgreSQL، مع معاملات ذرية وقفل سجلات الفواتير أثناء التوزيع، ثم إضافة دفتر الأستاذ والقيود المزدوجة والموافقات وسجل التدقيق. يوجد تصور مبدئي للبيانات في `BACKEND_DATA_MODEL_DRAFT.md`، وهو مستند تصميم وليس ترحيل قاعدة بيانات.
